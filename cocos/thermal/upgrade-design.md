# 温控升档（恢复）逻辑 · 技术设计

> 状态：一期设计，未实现。配套方案文档见 `D:\data\笔记\温控\4、一期方案.md`。
> 目标：解决"只降不升"——软温控在微信小游戏拿不到温度、限帧又让帧时间失真，必须有可靠的升档（恢复满帧）机制。

## 一、问题背景：为什么升档这么难

温控降档的信号是"帧时间超预算"，这个信号在限帧下**可靠**（负载重 → 帧时间真的超预算）。
但升档需要反向信号"负载变轻了"，而软温控只有帧时间一个信号，它在限帧下**失真**：

- 微信小游戏跑 60Hz 屏，引擎限帧（`game.frameRate`）是"RAF 仍 60Hz 触发、每隔 N 帧才 tick"。
- 降到 30fps 后，每帧实际间隔被拉长到 33.33ms，**无论负载多重多轻，帧时间都≈预算**。
- 所以"帧时间低于预算 X%"这个信号，在限帧下永远测不出"真实有余力"。

三个可能信号全部失效：
1. 温度 —— 微信运行时拿不到。
2. 帧时间低于预算 —— 限帧拉平，失真。
3. GPU 真实耗时 —— 微信不提供，JS 侧只能测帧间隔。

**结论：软温控没有被动信号能判断"该升档了"，只能主动试探（probe）。**

## 二、核心思路：试探式升档（probe-based recovery）

没有被动信号，就主动试探：

> 定时主动升一档 → 观察升档后帧时间能否稳住 → 稳住就保持，稳不住就**定向撤销刚升的那档**并退避。

这等价于 TCP 拥塞控制的思路：不知道还有没有余量，就试着加一点，加了会"丢包"（帧时间超预算）就退回来，失败越多试得越稀。

### 升档顺序：手动与自动分开（关键决策）

手动升档和自动试探的**诉求相反**，必须分开：

| 场景 | 顺序 | 理由 |
|---|---|---|
| **手动 `stepUp()`** | `frameRate-first`（先回帧率，再回分辨率） | 用户手动升档最想要 FPS 先回来，立即改善观感。**保持现网行为不变。** |
| **自动试探** | `scale-first`（先升分辨率，满后再升帧率） | 分辨率多档、可逐档渐进；帧率档少（30→60 一跳幅度大），大跳放最后。**对自动探测更稳。** |

> ⚠️ **scale-first 的"小步"不成立的首步**：现网分辨率档位是 `[1.0, 0.85, 0.7, 0.3]`，若当前在 0.3，自动试探的第一档是 0.3→0.7，是 **2.3× 像素跳，并非小步**。一期不补中间档（0.5/0.6），接受"首步是大步"，靠**失败退避**兜底（大步探一下、不行就退避翻倍）。补细档位留二期。

> 帧率档位：60Hz 屏下帧率只能是 60 的整数因子（60/30/20/15）。45 会造成帧间隔 16.7ms/33.3ms 交替 → judder。
> 所以帧率档位由 `minFrameRate` 决定：[60,30] 或 [60,30,20] 或 [60,30,15]，升档是"从地板逐档升到 60"，不是固定"30↔60 两档跳"。

## 三、升档状态机（自动试探）

```
                     ┌──────────────────────────────┐
                     │   空闲（无试探进行中）        │
                     └──────────────────────────────┘
                            │ 到达 probeIntervalSeconds
                            ▼
                     ┌──────────────────────────────┐
                     │ 试探升一档（内部 force=false）│
                     │ 记录 _upProbeLever/_upProbeAt│
                     └──────────────────────────────┘
                            │
              ┌─────────────┴─────────────┐
              │ 观察 recoveryProbeSeconds │（默认 15s）
              ▼                           ▼
    帧时间超预算 → 降档            帧时间稳在预算内
              │                           │
              ▼                           ▼
    ┌────────────────────────┐   ┌────────────────────────┐
    │ 判定失败                │   │ 判定成功                │
    │ 定向撤销刚升的杠杆      │   │ 保持，清失败计数        │
    │ 退避翻倍                │   │ 立即试探下一档（不等待）│
    └────────────────────────┘   └────────────────────────┘
              │                           │
              ▼                           ▼
     下次试探间隔 ×2              直到升满（scale=1.0 且
                                 frameRate=天花板）→ 停探测定时器
```

## 四、参数设计

| 参数 | 默认 | 职责（明确定死） |
|---|---|---|
| `probeIntervalSeconds` | 60 | **降档后到"第一次"试探的静默期**。成功后立刻继续下一档时**不经过它**，只有"从空闲态启动新一轮试探"才用它 |
| `recoveryProbeSeconds` | 15（已有） | 升档后观察多久判定成败。**15s 为初值，需真机长测标定；若边界负载出现"刚撑过 15s、下一档就翻车"的锯齿，延长到 30s。** |
| `recoveryBackoffSeconds` | 60（已有） | 失败后退避的**基数**，`下次试探间隔 = recoveryBackoffSeconds × 2^(失败次数-1)`，封顶 `recoveryBackoffMaxSeconds` |
| `recoveryBackoffMaxSeconds` | 600（已有） | 退避封顶 |

> 退避基数明确是 `recoveryBackoffSeconds`，不是 `probeIntervalSeconds`（二者职责不同：前者是失败退避基数，后者是首次试探静默期）。

## 五、与现有代码的衔接

现有 `thermal-controller.ts` 已经埋好了退避骨架，升档逻辑需补"试探触发器"。

已存在（复用）：
- `_upProbeLever` / `_upProbeAt`：记录哪次升档、何时升的。
- `_recordRecoveryFailure`：升档后 `recoveryProbeSeconds` 内又降档 → 判定失败，写退避状态。
- `_recoveryBackoffMs` / `_recoveryBackoffMaxSeconds`：指数退避计算。
- `_isUpBlocked`：退避期内不试。
- `_doStepUp(force)`：`force=false` 时走 `_isUpBlocked` 检查。

要实现（新增）：
1. **试探触发器**：降档后启动定时器，到 `probeIntervalSeconds` 调 **`_doStepUp(..., force=false)`**（内部入口，**绝不调公开 `stepUp()`**，否则 force=true 绕过退避、振荡控制失效）。
2. **自动升档顺序**：新增 scale-first 的自动试探路径（手动 `stepUp()` 保持现网 frameRate-first 不变）。
3. **失败定向撤销**：观察窗口内又降档时，**定向撤销 `_upProbeLever` 对应的那个杠杆**，不走通用 `_doStepDown`（通用降档是 scale-first，会级联降分辨率，语义错误）。
4. **成功判定**：观察窗口内没降档 → 清失败计数，**立即试探下一档**（不等待 probeIntervalSeconds）。
5. **停止条件**：升到 scale=1.0 且 frameRate=天花板后，停掉探测定时器，避免空转。

## 六、失败定向撤销（关键语义）

探测失败时，**撤销的是"刚升的那个杠杆"**，不是"重新走一遍降档流程"。

举例（自动试探 scale-first，当前 scale=1.0、frameRate=30）：
- 试探升帧率 30→60 → 观察 15s 内帧时间超预算。
- 失败 → **定向撤销帧率 60→30**（撤销刚升的那步），而不是走通用降档（通用降档会先降 scale 1.0→0.85，级联错误）。

实现方式：`_doStepDown` 里若 `_upProbeLever` 存在（说明处于升档观察期），降档时**优先撤销 `_upProbeLever` 那个杠杆**，而不是按 scale-first 通用顺序。

## 七、二期演进方向

二期接入真实温度/headroom 信号后，把"定时试探"升级成"信号驱动试探"：
- 温度低于阈值才启动试探升档（更精准，不会在温度还高时瞎试）。
- 一期先跑通"定时试探 + 退避"这个骨架，二期换触发源，状态机不用改。

## 八、已定案决策

1. **升档顺序分开**：手动 `stepUp()` 用 frameRate-first（保持现网）；自动试探用 scale-first。不合并成一个全局开关。
2. **试探成功后立即继续下一档**：不等待 probeIntervalSeconds，直到升满或某档失败。
3. **手动 `stepUp()` 保留绕过退避**：退避只约束自动试探；手动是用户明确意图、应立即响应。副作用（手动升档后若又自动降档，仍记录失败）是良性的。
4. **失败定向撤销**：撤销刚升的杠杆，不走通用 scale-first 降档。
5. **触发器走内部 force=false 入口**：绝不调公开 stepUp()。
6. **升档方案纳入一期**：见方案文档 §2.2。
